# Локальный Telegram-бот через long polling — спецификация

**Дата:** 29 августа 2026 года  
**Статус:** архитектура утверждена пользователем  
**Проект:** «Сладкая история»

## Контекст

Сайт работает локально на `http://localhost:3000`. Отправка заявок владельцу через Telegram Bot API уже реализована в `app/api/orders/route.ts`. Диалоговый AI-менеджер, база знаний, команды `/start`, `/help`, `/reset`, краткая история диалога и подключение LLM Router уже реализованы в `app/api/telegram/webhook/route.ts` и `app/lib/bakery-knowledge.ts`.

Текущий входящий транспорт рассчитан на Telegram webhook. Telegram не может отправлять webhook-запросы на `localhost`, а публичный хостинг и HTTPS-туннель исключены требованием пользователя. Поэтому отправленный в Telegram `/start` не попадает в локальный обработчик.

## Цель

Добавить локальный процесс long polling, который получает входящие Telegram-сообщения официальным методом `getUpdates`, передаёт их существующему обработчику на `localhost:3000` и позволяет AI-менеджеру отвечать через `sendMessage`.

Сайт, обработчик заявок и бот должны запускаться одной Windows-командой. Связь с Telegram и LLM Router требует подключения компьютера к интернету, но веб-интерфейс остаётся доступным только локально.

## Не входит в объём

- публичное размещение сайта, Cloudflare Tunnel, ngrok и другие внешние туннели;
- постоянное хранение истории диалогов;
- CRM, аналитика, роли владельца и покупателя;
- обработка фотографий, голосовых сообщений, файлов и платежей;
- изменение каталога, дизайна сайта или формы заказа;
- одновременная работа webhook и long polling.

## Выбранная архитектура

```text
Telegram Bot API
      |
      | getUpdates (long polling)
      v
scripts/telegram-polling.mjs
      |
      | POST + x-telegram-bot-api-secret-token
      v
http://127.0.0.1:3000/api/telegram/webhook
      |
      +--> база знаний сайта
      +--> LLM Router / gemini-3-flash
      +--> Telegram sendMessage
```

Локальный poller выполняет только транспортную функцию. Он не копирует бизнес-логику AI-менеджера и не знает ассортимент кондитерской. Существующий HTTP-обработчик остаётся единой точкой обработки Telegram update для команд, диалоговой памяти, rate limit, обращения к модели и отправки ответа.

## Компоненты

### 1. Чистое ядро polling

Файл `scripts/telegram-polling-core.mjs` содержит независимо тестируемые функции:

- формирование URL Telegram Bot API;
- вызов `getUpdates` с `offset`, `timeout` и `allowed_updates`;
- проверка поля `ok` и структуры ответа Telegram;
- защищённая передача одного update в локальный webhook;
- вычисление следующего `offset` как `update_id + 1`;
- расчёт ограниченной задержки повторной попытки.

Функции получают `fetch` как зависимость. Это позволяет тестировать реальные HTTP-контракты без обращения к Telegram, LLM Router и локальному серверу.

### 2. Локальный процесс бота

Файл `scripts/telegram-polling.mjs`:

1. Проверяет наличие `TELEGRAM_BOT_TOKEN` и `TELEGRAM_WEBHOOK_SECRET`.
2. Вызывает `deleteWebhook` с `drop_pending_updates: false`, чтобы Telegram разрешил `getUpdates` и сохранил уже отправленные сообщения.
3. Запускает long polling с таймаутом 25 секунд и получает только обновления типа `message`.
4. Передаёт обновления в локальный webhook строго последовательно.
5. Продвигает `offset` только после успешного HTTP-ответа локального обработчика.
6. При временной ошибке повторяет цикл с задержкой 1, 2, 5 и далее максимум 10 секунд.
7. Корректно завершает текущий запрос по `Ctrl+C` и освобождает процесс.

Если локальный сайт недоступен, update не подтверждается увеличением `offset` и будет обработан после восстановления сайта. Обновления из одной пачки не обгоняют неуспешное обновление.

### 3. Существующий webhook как локальный мост

Маршрут `app/api/telegram/webhook/route.ts` продолжает проверять заголовок `x-telegram-bot-api-secret-token`. Poller использует тот же `TELEGRAM_WEBHOOK_SECRET`, что и локальный сервер.

Обработчик должен возвращать неуспешный HTTP-статус, если финальная отправка ответа в Telegram не состоялась. Запись update как обработанного выполняется только после успешного завершения ветки. Это не позволяет poller безусловно подтвердить потерянный ответ.

Команды `/start`, `/help`, `/reset`, системная инструкция менеджера, база знаний и ограничение истории остаются совместимыми с текущим поведением.

### 4. Локальный запуск

В `package.json` добавляются команды:

- `npm run bot` — запуск poller через Node.js 22 с загрузкой `.env.local`;
- `npm test` — запуск тестов Node Test Runner.

Корневой `start-site.bat` становится единым локальным лаунчером:

1. переходит в каталог `site`;
2. проверяет или запускает production-сервер;
3. ждёт `HTTP 200` от `http://127.0.0.1:3000`;
4. запускает один экземпляр poller;
5. записывает раздельные журналы сайта и бота;
6. открывает `http://localhost:3000`.

Повторный запуск не должен создавать второй сервер или второй poller. Если Telegram сообщает `409 Conflict`, журнал объясняет, что уже работает другой экземпляр `getUpdates`.

### 5. Локальная конфигурация

Для локальной разработки используются:

```dotenv
TELEGRAM_BOT_TOKEN=секретный_токен
TELEGRAM_CHAT_ID=id_получателя_заявок
TELEGRAM_MESSAGE_THREAD_ID=
TELEGRAM_WEBHOOK_SECRET=случайный_локальный_секрет
LLM_ROUTER_API_KEY=секретный_ключ
LLM_ROUTER_BASE_URL=https://llm-router.org/v1
LLM_ROUTER_MODEL=gemini-3-flash
SITE_URL=http://localhost:3000
LOCAL_TELEGRAM_WEBHOOK_URL=http://127.0.0.1:3000/api/telegram/webhook
```

`.env.local` остаётся исключённым из Git. Лаунчер, poller и журналы не выводят значения токенов, API-ключей или webhook-секрета.

Ссылка `SITE_URL=http://localhost:3000` открывается только на компьютере, где работает сайт. Сам Telegram-бот доступен пользователям с других устройств, пока локальный компьютер, сайт, poller и интернет-соединение работают.

## Поток данных

### Команда `/start`

1. Пользователь отправляет `/start` боту.
2. Telegram сохраняет update.
3. Poller получает update через `getUpdates`.
4. Poller отправляет update на локальный webhook с секретным заголовком.
5. Webhook формирует существующее приветствие и вызывает `sendMessage`.
6. После успешного ответа webhook poller увеличивает `offset`.

### Обычный вопрос покупателя

1. Poller передаёт текст и идентификатор чата в webhook.
2. Webhook добавляет до четырёх последних пар сообщений.
3. LLM Router получает системную инструкцию, базу знаний и диалог.
4. Ответ нормализуется: он ограничен по длине и завершается вопросом.
5. Telegram получает ответ; только затем update подтверждается новым `offset`.

### Заявка с сайта

Поток формы не зависит от poller. `app/api/orders/route.ts` продолжает напрямую отправлять владельцу структурированное сообщение через `sendMessage` и возвращает сайту номер заказа только после подтверждения Telegram.

## Ошибки и восстановление

- **Telegram временно недоступен:** poller повторяет запрос с ограниченной задержкой.
- **Локальный сайт ещё не запущен:** update остаётся неподтверждённым; poller повторяет передачу после восстановления сервера.
- **LLM Router недоступен:** webhook использует существующий безопасный ответ-заглушку и пытается отправить его покупателю.
- **Отправка ответа Telegram не удалась:** webhook возвращает ошибку, poller не продвигает `offset`.
- **Неверный локальный секрет:** webhook возвращает `401`, poller сообщает только название отсутствующей или несовместимой настройки без её значения.
- **Другой poller уже работает:** Telegram возвращает `409`; процесс не запускает конкурирующий цикл и объясняет причину в журнале.
- **Повторная доставка update:** обработчик подавляет уже успешно завершённый `update_id` в рамках жизни локального сервера.
- **Остановка компьютера:** бот перестаёт отвечать; Telegram хранит неподтверждённые обновления в пределах собственных сроков хранения.

## Тестирование

Используется встроенный `node:test`, без новой тестовой библиотеки.

Автоматические тесты проверяют:

1. `getUpdates` получает правильные `offset`, `timeout` и `allowed_updates`.
2. Ответ Telegram с `ok: false` считается ошибкой.
3. Update передаётся на `127.0.0.1:3000` с JSON и правильным именем секретного заголовка.
4. `offset` увеличивается только после успешного ответа локального webhook.
5. При ошибке пачка останавливается на первом неуспешном update.
6. `deleteWebhook` сохраняет накопленные обновления.
7. Повторные задержки ограничены десятью секундами.
8. Значения секретов не попадают в сообщения об ошибках.

Финальная проверка включает:

- `npm test`;
- `npm run lint`;
- `npm run build`;
- `HTTP 200` от `http://127.0.0.1:3000`;
- запуск poller через единый лаунчер;
- подтверждение, что Telegram webhook отключён;
- реальный ответ `@history_sweet_bot` на `/start` и один вопрос об ассортименте;
- отсутствие секретов в Git diff и журналах запуска.

## Критерии готовности

- сайт открывается только на `localhost:3000`;
- одна команда запускает сайт и локального Telegram-бота;
- уже отправленный `/start` обрабатывается без публичного webhook;
- бот отвечает на вопросы строго по базе знаний сайта и заканчивает ответ уместным вопросом;
- заявки с формы продолжают приходить владельцу в понятном сообщении;
- временный разрыв связи не требует изменения кода или повторной настройки токенов;
- тесты, lint и production-сборка завершаются успешно;
- секретные значения отсутствуют в отслеживаемых файлах и журналах.
